# ADR 001: المعمارية الأمنية وهيكل قاعدة البيانات لمنصة عقار إكزت

- **الحالة:** معتمد (Approved)
- **التاريخ:** 26 أكتوبر 2026
- **المؤلف:** الفريق التقني لمنصة عقار إكزت
- **النطاق:** قاعدة البيانات، سياسات RLS، سجل التدقيق، وبوابات النشر

---

## 1. السياق والمشكلة (Context & Problem Statement)

منصة **عقار إكزت (Aqar Exit)** تعمل في سوق العقارات المصري لتنظيم عمليات التنازل عن وحدات التقسيط بدون أوفر. هذه العمليات تتضمن:
1. مستندات بالغة الحساسية: عقود المطورين الأصلية، إيصالات السداد البنكية، كشوف الحسابات، وصور بطاقات الرقم القومي.
2. أرقام مالية متغيرة: مبالغ مدفوعة، أقساط متبقية، غرامات تأخير، ورسوم تنازل يفرضها المطور.
3. متطلبات خصوصية عالية: حظر نشر أي بيانات شخصية للبائع أو أرقام هواتفه أو صور مستنداته للعامة.
4. الحاجة لتسجيل تدقيق غير قابل للتلاعب (Audit Trail) لضمان المساءلة في كل قرار مراجعة أو تغيير حالة.

---

## 2. القرارات المعمارية المعتمدة (Architectural Decisions)

### أ. الفصل الصارم بين الكيانات (Entity Separation)
تم تجنب التصاميم المسطحة التي تدمج العقار بالطلب بالعقد. الهيكل يفصل كالتالي:
- `properties`: يمثل العقار الفيزيائي (المحافظة، المدينة، المشروع، المطور، المساحة، نوع الوحدة).
- `contracts`: يمثل الاتفاق المالي الأصلي مع المطور (إجمالي التعاقد، الدفعة المقدمة، الأقساط، التكرار).
- `assignment_cases`: يمثل طلب التنازل نفسه ودورة حياته وإدارته.
- `case_financial_snapshots`: يسجل كل تعديل أو مراجعة مالية مع المصدر والتاريخ ونسبة الثقة.
- `case_documents`: يسجل بيانات المستندات في Private Storage مع حالة التحقق.
- `financial_reviews` & `legal_reviews`: قرارات المراجعة المستقلة وفق مبدأ أقل صلاحية.
- `leads` & `deals`: متابعة المشترين والوساطة والتنازل النهائي بمقر المطور.

### ب. تتبع المبالغ ومصادرها (Amount Tracking & Confidence)
كل مبلغ يسجل ومعه حقول:
1. `amount`: القيمة بالجنيه المصري (ممنوع القيم السالبة `CHECK (amount >= 0)`).
2. `confidence`: تصنيف الثقة (`confirmed_by_documents`, `seller_declared`, `estimated`, `requires_verification`).
3. `source_description`: مصدر الرقم (مثلاً: "كشف حساب معتمد من شركة سوديك بتاريخ 15-01-2026").
4. `verified_at` & `verified_by`: تاريخ وهوية المسؤول الذي دقق الرقم.

### ج. حماية سجل التدقيق (Audit Log Immutability)
1. جدول `audit_logs` محمي بواسطة PostgreSQL Trigger يمنع عمليات `UPDATE` و `DELETE` تماماً:
   - أي محاولة تعديل أو حذف تُلقي استثناءً فورياً: `RAISE EXCEPTION 'Audit logs are immutable'`.
2. سياسات RLS تحظر أي إدخال يدوي من المستخدمين العاديين، وتسمح بالقراءة فقط لمديري النظام `admin` و `system_admin`.
3. **تنبيه قانوني وتقني موثق:**  
   > ⚠️ **إخلاء مسؤولية أمني:** الحماية البرمجية عبر Triggers و RLS تمنع التلاعب عبر واجهات التطبيق ومستخدمي قاعدة البيانات العاديين. ومع ذلك، **لا تمثل ضماناً مطلقاً ضد مسؤول قاعدة بيانات (DB Superuser / Postgres Role)** يمتلك صلاحيات مرتفعة مباشرة على خادم قاعدة البيانات، حيث يمكن لمالك الخادم تعطيل الـ Triggers أو التعديل المباشر. لضمان أقصى موثوقية إنتاجية، يُوصى بتفعيل Write-Once-Read-Many (WORM) أو إرسال سجلات التدقيق إلى خدمة تخزين سجلات سحابية خارجية مستقلة (مثل AWS CloudWatch Logs أو Datadog) مع قفل صلاحيات الحذف.

### د. أمان الكتالوج العام عبر Safe View (`public_verified_listings_view`)
- لضمان عدم تسريب أي بيانات شخصية (PII) أو أرقام هواتف أو مستندات أو ملاحظات تعثر خاصة للبائع، تم إنشاء View مخصصة مع خاصية `WITH (security_barrier = true)`.
- الـ View ترجع فقط الحالات ذات `status = 'published'` و `is_private_listing = false`.
- الحقول المعادة هي فقط بيانات العقار العامة، المبالغ المحققة، موعد الاستلام، وتاريخ آخر مراجعة.

### هـ. بوابات النشر الـ 9 (Publication Gates)
لا يمكن نشر أي وحدة إلا بعد استيفاء جميع البوابات التالية خادمياً:
1. `gate_1_complete_unit_data`: اكتمال بيانات الوحدة والمشروع والمطور.
2. `gate_2_seller_identity_confirmed`: التحقق من هوية البائع وصلاحيته للبيع.
3. `gate_3_mandatory_docs_verified`: رفع العقد وإيصالات السداد والتحقق منها.
4. `gate_4_financial_review_approved`: اعتماد المراجعة المالية بالأرقام والمصادر.
5. `gate_5_legal_review_approved`: صدور قرار قانوني إيجابي (`eligible` أو `eligible_with_conditions`).
6. `gate_6_developer_transfer_clear`: وضوح موقف المطور ورسوم التنازل وإمكانية التنازل.
7. `gate_7_publisher_authorized`: توقيع مسؤول النشر المعتمد (`publisher`).
8. `gate_8_pii_sanitized_for_public`: خلو الإعلان من أي بيانات اتصال أو مستندات خاصة.
9. `gate_9_disclaimers_and_timestamp_ready`: تضمين إخلاء المسؤولية وتاريخ آخر تحقق.

---

## 3. العواقب والآثار (Consequences)
- **الإيجابيات:** حماية قانونية للمنصة، عزل بيانات البائعين، مصداقية تامة أمام المشترين، وسجل غير قابل للتلاعب داخل التطبيق.
- **التحديات:** تطلب مراجعة بشرية متأنية لكل حالة قبل النشر (وهو المطلوب تماماً في نموذج العمل لتجنب الأخطاء القانونية).
